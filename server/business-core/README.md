# SEYVEO Business · серверный фундамент (пока не развернут)

Отдельный серверный модуль для будущего SEYVEO Cloud / Hybrid / Private. Он **не подключён** к GitHub Pages, приложению SEYVEO, настоящим людям или корпоративным серверам. Нет работающей регистрации, доставки приглашений, сессий, API или продакшен-базы.

## Что уже в коде

- `migrations/001_business_identity.sql`: PostgreSQL-таблицы пользователей, организаций, филиалов, отделов, членств, назначенных ролей, приглашений с одноразовым токеном и журнала аудита.
- `policy.cjs`: fail-closed проверка действий для одной организации и рабочего контекста по роли, филиалу и назначению документа; *не* реализует верификацию личности.
- `test/policy.test.cjs`: тесты разграничения организаций, права читать документы, назначать сотрудников и недоступности личного сейфа.

Требования к окружению: Node.js >= 20 (для `node:test`) и PostgreSQL >= 14 для схемы. Тесты не требуют PostgreSQL.

```sh
cd server/business-core
node --test test/policy.test.cjs
```

## Границы доверия

**Критически важно:** `checkPermission(actor,action,resource)` принимает `actor` **только из серверного проверенного session context и базы членств**. Запрещено передавать туда объект от клиента, `window.SEYVEO_PREVIEW`, пользовательский JSON, ID организации из несверенного URL или роль из локального хранилища. Проверять, что membership активен, организация не приостановлена, роль не отозвана, сессия не истекла, а целевой ресурс принадлежит запрошенной организации.

Любой SQL запрос должен быть с `organization_id` и требуемой проверкой полномочий; БД RLS/раздельные учётные данные — дополнительные слои, но не замена серверной политики. Пароли, одноразовые токены, ключи ЭП и данные документов запрещено хранить в логе или браузерном localStorage.

Текущий policy-модуль **специально не поддерживает** юридически значимое подписание, удаление документов, внешнюю отправку от имени организации, банковские действия и любые неизвестные права. Эти операции требуют отдельных проверок, состояния документа, полномочий/МЧД, повторного подтверждения человека и подтверждения официального сервиса.

## Следующие задачи до первого живого приглашения

1. Выбрать зарегистрированного провайдера аутентификации и стратегию сессий, подтверждение телефона/почты, создание пользователя.
2. Поднять защищённый HTTPS backend, PostgreSQL, миграции и секреты на изолированном сервере. Статический GitHub Pages сам не может держать безопасные секреты.
3. Реализовать API и транзакции `/me/work/invitations`: создание уполномоченным кадровиком/руководителем, проверка адресата, одноразовость, время жизни, атомарное принятие, идемпотентность, отзыв.
4. Серверная проверка ролей при **каждом** чтении или изменении. Смену роли, отзыв доступа и перевод сотрудника фиксировать в аудите и отменять рабочие сессии.
5. Провести автоматические тесты HTTP и БД, конкурентных принятий приглашений, межорганизационных утечек, CORS, CSRF, rate limits, отказов, резервных копий и восстановления.
6. Только после этого подключать API к рабочим кабинетам, карточкам Главной и чату Сэйви, исключив демонстрационные права из production-пути.
